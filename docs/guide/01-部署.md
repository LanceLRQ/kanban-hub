# 部署

kanban-hub 的服务端是一个 Next.js 应用，数据存成文件，不需要数据库。部署有三种方式：

| 方式 | 适合 |
|---|---|
| 一键脚本 | Linux 宿主机，装有 Docker，想少操心 |
| 手动 Docker Compose | 想自己管 compose 文件，或者要从源码构建镜像 |
| systemd 直接运行 | 不想用 Docker，宿主机有 Node 22 和 git |

服务默认监听 `28970` 端口。部署完成后，浏览器打开 `http://<服务器地址>:28970`，用管理员密码登录。

## 一键脚本

只支持 Linux 宿主机，需要事先装好 Docker 和 Docker Compose 插件。

```bash
curl -fsSL https://raw.githubusercontent.com/LanceLRQ/kanban-hub/main/deploy/kanban-hub.sh | bash
```

向导会依次问你安装目录、端口和监听地址、管理员密码（可以让它随机生成）、时区、运行身份和对外地址。你确认之前，它不会写任何文件。确认后，它会建好 `data/`、`backups/` 目录并对齐属主，然后拉取镜像启动。

安装完成后，脚本会复制一份到安装目录里。以后在安装目录下运行它来管理服务：

```bash
bash kanban-hub.sh              # 打开管理菜单
bash kanban-hub.sh status       # 运行状态
bash kanban-hub.sh logs -f      # 持续查看日志
bash kanban-hub.sh config       # 修改配置
bash kanban-hub.sh restart      # 改完配置后重建并重启
bash kanban-hub.sh doctor       # 环境自检
bash kanban-hub.sh upgrade      # 升级到最新正式版
bash kanban-hub.sh upgrade --to 0.2.0   # 升级到指定版本
bash kanban-hub.sh restore <备份文件名>  # 从备份恢复，见《备份与恢复》
bash kanban-hub.sh uninstall    # 卸载
```

`upgrade` 会先更新脚本自身，再同步 compose 模板。如果你手改过 compose 文件，它会把差异列出来，等你确认后再覆盖。

脚本要求当前用户能读写安装目录和其中的 `.env`。用 sudo 安装的，之后也要用 sudo 管理。

## 手动 Docker Compose

```bash
git clone https://github.com/LanceLRQ/kanban-hub.git
cd kanban-hub/deploy
cp .env.example .env        # 至少填好 KH_ADMIN_PASSWORD、PUID、PGID
mkdir -p data backups       # 必须先建好，原因见下文“文件属主”
docker compose up -d --build
```

仓库里的 `deploy/docker-compose.yml` 从源码构建镜像。想直接用 Docker Hub 上的镜像，把 `image` 改成 `lancelrq/kanban-hub:<版本>`，删掉 `build` 段。镜像有 amd64 和 arm64 两种架构。

容器自带健康检查，访问的是 `/api/health`。用 `docker compose ps` 能看到健康状态。

## 环境变量

写在 `deploy/.env` 里（一键脚本写在安装目录的 `.env` 里）。

| 变量 | 默认值 | 说明 |
|---|---|---|
| `KH_ADMIN_PASSWORD` | 无，必填 | 管理员密码的唯一来源。改了之后重启，所有网页登录会话失效；已接入机器的令牌不受影响 |
| `PUID` / `PGID` | `1000` | 容器的运行身份。填宿主机上 `id -u`、`id -g` 的结果，这样数据文件归你所有 |
| `UMASK` | `022` | 新建文件的权限掩码。需要同组用户可写时改成 `002` |
| `KH_BIND` | `0.0.0.0` | 监听地址。放在反向代理后面时改成 `127.0.0.1` |
| `KH_PORT` | `28970` | 宿主机端口 |
| `KH_PUBLIC_URL` | 空 | 服务的对外地址，例如 `https://kanban.example.com`。它会写进接入引导发给 AI 的那句话里，也是网页写操作做同源校验时信任的来源。留空时从请求的 Host 推断。必须是合法的 http/https 地址，否则服务拒绝启动 |
| `KH_STALE_DAYS` | `7` | 项目多少天没有任何事件就标为停滞 |
| `TZ` | `Asia/Shanghai` | 时区。影响备份文件名、导出 Markdown 里的时间 |
| `KH_IMAGE_TAG` | `local` | 本地构建时给镜像打的标签 |
| `HTTP_PROXY` / `HTTPS_PROXY` | 空 | 构建镜像时使用的代理 |

## 反向代理与 HTTPS

在局域网里直接用 HTTP 也能工作，但机器令牌、登录密码和备份密码都会明文传输。要跨网络使用，建议放在 HTTPS 反向代理后面：

1. `KH_BIND` 改成 `127.0.0.1`，只让代理访问。
2. 代理如果会改写 Host 头，设置 `KH_PUBLIC_URL` 为对外地址，或者让代理保留原始 Host。不这样做，网页上的写操作会因为同源校验失败而被拒绝。
3. 网页通过 SSE（`/api/v1/stream`）接收实时更新。这个接口的响应带 `X-Accel-Buffering: no`，nginx 会据此关闭缓冲；其他代理如果会缓冲响应，要对这个路径手动关掉。

HTTP/2 还有一个好处：每个打开的标签页都要占一条 SSE 长连接，浏览器在 HTTP/1.1 下对同一主机通常只开 6 条连接，标签页开多了会卡住。HTTP/2 没有这个限制。

## 文件属主

容器不以 root 运行，而是以 `PUID:PGID` 的身份写 `/data` 和 `/backups`。有两点要注意：

- 挂载目录要在启动前用 `mkdir -p data backups` 建好。宿主机上不存在的目录会被 Docker 以 root 身份创建，之后容器就写不进去了。
- 启动时服务会自检：目录不存在、不可写，或者同一个数据目录已经有另一个进程在用，都会直接退出，并在日志里给出要执行的 `chown` 命令。

一键脚本的向导和 `start` 命令会自动建目录、对齐属主，不用手动处理。

## 不用 Docker（systemd）

宿主机需要 Node 22 及以上和 git。

```bash
git clone https://github.com/LanceLRQ/kanban-hub.git /opt/kanban-hub
cd /opt/kanban-hub
pnpm install
pnpm -F @kanban-hub/web build
```

构建产物在 `apps/web/.next/standalone/`，入口是嵌套的 `apps/web/.next/standalone/apps/web/server.js`。

仓库里的 [`deploy/systemd/kanban-hub.service`](../../deploy/systemd/kanban-hub.service) 是一份可以直接改的 unit 示例，要点：

- 数据目录和备份目录用 `KH_DATA_DIR`、`KH_BACKUP_DIR` 指定，必须是绝对路径。standalone 启动时会切换工作目录，相对路径会指错地方。
- 保留 `NEXT_MANUAL_SIG_HANDLE=1`。关机时应用会先把未提交的改动提交进 git 再退出。
- `TimeoutStopSec` 要大于 8 秒，给关机留出时间。
- 管理员密码放在 `EnvironmentFile` 指向的单独文件里，权限设为 600。

没有设置 `KH_DATA_DIR` 时，数据目录默认是 `~/.kanban-hub/server/data`。

## 数据目录里有什么

```
data/
├── auth/                     # 用户、机器、会话签名密钥（不进 git 历史，但会打包进备份）
└── projects/<项目ID>/
    ├── project.yaml          # 项目信息
    ├── board.yaml            # 容器和任务
    ├── events/2026-09.jsonl  # 事件，按月分文件
    ├── manifests/            # 各机器文档快照的清单
    └── snapshots/<机器ID>/    # 各机器同步上来的文档
```

`data/` 本身是一个 git 仓库。每次写入后安静 30 秒，服务会提交一次，按操作者分成不同的提交。你可以在里面用 `git log` 查看历史，但不要手动修改文件，服务运行时以内存里的状态为准。
