# 接入机器与仓库

服务端跑起来之后，还要做两件事：让开发机上的 `kh` 登录服务端，再把仓库注册成项目。这两件事都可以交给 AI 助手去做，你只需要在网页上生成配对码，再在它问你的时候点头。

## 最省事的做法：交给 AI

1. 打开网页的接入引导页 `/setup`（在顶栏的“设置”下面）。
2. 在“登录本机”一步点“生成配对码”。每次生成的配对码都不一样，是 6 位字母数字，中间带一个连字符。页面会把服务端地址和这次的配对码填进一句话里，格式如下：

   > 请按 `<服务端地址>/setup/agent.md` 的说明把本机接入 kanban-hub，配对码 `<配对码>`。

3. 把这句话发给你的 AI 助手（Claude Code、Codex、Gemini CLI、Cursor 等都可以）。

`agent.md` 会让 AI 按下面的顺序操作：检查 Node 和 git 版本，安装 `kh`，核对版本，登录，先用 `kh setup --dry-run` 给你看计划、等你同意后再安装 skill 与 hook。如果当前目录是仓库，它会问你要不要接着接入这个仓库。遇到权限问题（比如全局安装要 sudo），它会先问你，不会自己加 sudo。

接入仓库也有一句可以复制的话，在同一页的“注册仓库”一步：

> 请按 `<服务端地址>/setup/migrate.md` 的说明把当前仓库接入 kanban-hub。

`migrate.md` 除了注册，还会让 AI 读懂仓库里已有的进度文档（比如 `TASKS.md`），整理成导入文件，给你预览后再导入。原来的进度文档不会被修改。

配对码 10 分钟内有效，只能用一次。过期了就回到 `/setup` 重新生成。

下面是手动操作的步骤，想了解细节或者 AI 卡住时可以参考。

## 安装 kh

开发机需要 Node 22 及以上和 git。安装包由服务端提供，版本与服务端一致：

```bash
npm i -g http://<服务端地址>/setup/kh.tgz
kh --version
curl -s http://<服务端地址>/api/health     # 返回的 version 应与上一行一致
```

`kh` 没有发布到 npm。服务端升级后，用同样的命令重新安装一次。版本不兼容时，`kh` 会以退出码 6 报错并提示重新安装。

## 登录

```bash
kh login --server http://<服务端地址> --code <配对码>
kh whoami
```

`--name` 可以给这台机器起名字，默认取主机名。名字之后也能在网页上改。

登录后，本机配置和令牌保存在 `~/.kanban-hub/`（可以用环境变量 `KH_HOME` 换一个绝对路径）。令牌文件的权限是 600。令牌长期有效，改管理员密码不会让它失效，只有在网页上吊销才会。

## 安装 skill 与 hook

```bash
kh setup --dry-run    # 只看计划
kh setup --yes        # 执行
```

`kh setup` 会做这些事：

- 把 kanban-hub skill 写到 `~/.agents/skills/kanban-hub/SKILL.md`。Codex、Gemini CLI、Cursor 等 agent 都会读这个目录。
- 检测到 `~/.claude/` 时，再往 `~/.claude/skills/kanban-hub/` 复制一份，并往 `~/.claude/settings.json` 合并两个 hook：会话开始时执行 `kh hook session-start`，每轮回复结束时执行 `kh hook stop`。

修改 `settings.json` 之前，它会先备份成同目录下的 `settings.json.bak-<时间>`。它只增删自己的两条 hook，其他配置原样保留。文件结构不对（比如不是合法 JSON）时，它什么都不写，并指出出错的位置。重复执行只会更新 skill，不会重复添加 hook。

hook 在新开的 Claude Code 会话里才生效。它依赖 PATH 里能找到 `kh`；从图形界面启动的 Claude Code 可能拿不到终端里的 PATH，这时请看《常见问题》。

skill 规定了 AI 什么时候上报、怎么上报。大意是：开始一个任务标成进行中，做完标成复核中，验证通过才标已完成；卡住了标挂起并写原因；需要你拍板或动手的，打上“待你处理”标记；干活时发现的新问题记进杂项，不打断手头的事。

## 注册仓库

在仓库根目录执行：

```bash
kh register --dry-run    # 先看计划
kh register              # 交互确认后执行
```

`kh register` 会用仓库第一个提交的 hash 当指纹去服务端查找。找到同指纹的项目，说明这是同一个仓库在另一台机器上的副本，它会建议关联到那个项目；找不到就新建。非交互写法：

```bash
kh register --name my-app --new --yes
kh register --bind k3v9 --yes              # 关联到已有项目（ID 至少 4 位前缀）
kh register --new --include "docs/**" --include "CLAUDE.local.md" --yes
```

注册会在仓库里写 `.kanban-hub/config.yaml`，并把 `.kanban-hub/` 加进 `.git/info/exclude`，所以它不会出现在 `git status` 里，也不会被提交。仓库的 `.gitignore` 不会被改动。想把配置入库，可以执行 `git add -f .kanban-hub`。

注册完成后会做一次首次同步，把文档推送到服务端。

不是 git 仓库也可以注册，只是没有指纹，换台机器时要用 `--bind` 手动关联。

## 同步范围

`.kanban-hub/config.yaml` 的内容大致如下：

```yaml
projectId: k3v9x2m7qa
sync:
  include: [docs/**, "*.md"]
  exclude: []
  maxFileSize: 5MB
pull:
  auto: true
```

| 字段 | 说明 |
|---|---|
| `sync.include` | 要同步的文件，glob 写法。注册时按目录结构给出建议：存在的 `docs/`、`doc/`、`design/` 目录，以及根目录下的 `*.md`；`--include` 会完全替代建议 |
| `sync.exclude` | 在 `include` 基础上排除的文件。`node_modules`、`.git`、`.next` 始终排除 |
| `sync.maxFileSize` | 单个文件的大小上限，默认 5MB，最大 20MB。超过的文件跳过，项目设置页会列出来 |
| `pull.auto` | 会话开始时是否自动从其他机器拉取文档，默认开启 |

同步范围不看 `.gitignore`。没进 git 的私有文档（比如 `notes/`、`CLAUDE.local.md`）照样会同步到服务端，这正是跨机器查看私有文档的用途。如果某些文件不想离开这台机器，把它们写进 `exclude`，或者收窄 `include`。

改完 `config.yaml` 后执行一次 `kh sync`，新的范围就会生效。

## 在另一台机器上接入同一个仓库

在第二台机器上重复“安装 kh”“登录”“安装 skill 与 hook”，然后在仓库副本的根目录执行 `kh register`。指纹相同，它会建议关联到已有项目。关联之后，两台机器的文档快照在服务端分开存放，网页上可以切换查看。

## 升级 kh 与 skill

服务端升级后，每台开发机都要做两件事：重新安装 `kh`，再执行 `kh setup` 更新 skill 与 hook。只重装 `kh` 不会更新 skill，AI 就不知道新版本加了哪些命令。

最省事的做法是把下面这段话发给这台机器上的 AI 助手，把 `<服务端地址>` 换成你的地址（例如 `http://192.168.1.10:38970`）：

```text
请帮我把这台机器上的 kanban-hub 命令行 kh 和它的 skill 升级到服务端的当前版本，服务端地址是 <服务端地址>。按顺序做：

1. 看现状：执行 `kh --version`，再请求 <服务端地址>/api/health，记下 JSON 里的 version。两者已经一致时，跳到第 3 步。
2. 重新安装 kh：执行 `npm i -g <服务端地址>/setup/kh.tgz`。需要 sudo 或遇到权限问题时先告诉我，不要自己加 sudo。装完再执行 `kh --version`，确认与 /api/health 的 version 一致；不一致就把两个版本号都告诉我。
3. 更新 skill 和 hook：先执行 `kh setup --dry-run`，把计划给我看，等我同意后再执行 `kh setup --yes`。
4. 验证：执行 `kh --help`，确认命令可用；如果当前目录是已经注册过的仓库，再执行一次 `kh status`，确认能连上服务端。

最后用几句话告诉我：升级前后的 kh 版本号、skill 更新到了哪些路径、有没有遇到问题。
```

也可以自己执行：

```bash
npm i -g <服务端地址>/setup/kh.tgz
kh --version             # 应与服务端 /api/health 里的 version 一致
kh setup --dry-run       # 看计划
kh setup --yes           # 更新 skill 与 hook
```

## 管理机器

网页的 `/setup` 页和 `/settings` 页都列出了已接入的机器，能看到系统和最后在线时间，可以改名或吊销。吊销后，那台机器上的 `kh` 会以退出码 3 报错，需要重新配对才能继续使用。

## 撤销接入

```bash
kh setup --uninstall    # 删除 skill，从 settings.json 移除两个 hook（同样先备份）
kh logout               # 删除本机令牌
npm rm -g @kanban-hub/cli
```

仓库里的 `.kanban-hub/` 目录可以直接删除。之后记得在网页上吊销这台机器。
