# 文档同步与冲突

kanban-hub 的服务端不读任何仓库的磁盘。你在网页上看到的文档，是各台机器上的 `kh` 推送上去的快照。这样服务端和开发机可以不在同一台机器上，一个项目也可以分散在好几台机器上。

同步只处理 `.kanban-hub/config.yaml` 里 `sync.include` 覆盖的文件，见《接入》的“同步范围”一节。

## 推送

```bash
kh sync
```

`kh sync` 只上传服务端还没有的内容，没变的文件不会重复上传。上传过程中断时，服务端的旧快照保持不变，下次重新同步即可。

装了 Claude Code hook 的话，你基本不用手动推送：每轮回复结束时，hook 会在后台推送一次。为了不拖慢会话，如果上次推送后什么都没变，而且距上次推送不到 10 分钟，它就直接跳过。所以网页上的“最后同步时间”可能比实际晚几分钟，手动执行 `kh sync` 则每次都会推送。

推送时顺带上报仓库的 git 状态：分支、最新提交、未提交的改动数、领先落后的提交数，显示在项目卡片和项目设置页上。

每台机器的快照在服务端分开存放，互不覆盖。

一些规则：

- 超过 `maxFileSize` 的文件不上传，在项目设置页的“跳过的文件”里列出。
- 指向目录的软链接不同步。指向文件的软链接，目标在仓库内时同步目标的内容，目标在仓库外或者已失效时跳过。
- 两个路径只差大小写（比如 `Readme.md` 和 `README.md`），服务端会拒绝整份清单，`kh` 会指出是哪两个路径。

## 跨机器读取

在一台机器上想参考另一台机器上没进 git 的文档，不用拉到本地，直接读：

```bash
kh docs ls                  # 列出其他机器快照里的文件
kh docs ls "notes/**"       # 按 glob 过滤
kh docs cat notes/plan.md
kh docs cat --from desktop notes/plan.md
```

不指定 `--from` 时，每个路径取其他机器里最新的那一份。

## 拉取

```bash
kh pull --dry-run    # 先看会发生什么
kh pull
```

拉取会把其他机器上的文档写进本地仓库，这是 `kh` 唯一会改动仓库文件的操作。它有几条底线：

- 被 git 跟踪的文件一律跳过。这些文件应该用 `git pull` 同步，kanban-hub 只负责没进 git 的文档。
- 拉取从不删除本地文件。对方删了某个文件，本地的照样保留。
- 本地删掉的文件，如果对方的版本是本机见过的旧内容，不会被拉回来。
- 只处理本机 `sync.include` 范围内的文件。

对每个文件，`kh` 会比较三份内容：本地当前的、对方的，以及两边上一次一致时的“基准”。结果有这几种：

| 情况 | 结果 |
|---|---|
| 本地没有这个文件 | 新建 |
| 本地没改过，对方改了 | 用对方的覆盖 |
| 本地改过，对方没改 | 保留本地 |
| 对方是在本地当前版本的基础上改的 | 直接覆盖 |
| 两边都改了，是文本，改的地方不重叠 | 自动合并，写入本地 |
| 两边都改了，改的地方重叠，或者是二进制文件 | 登记为冲突，本地文件不动 |
| 对方的内容是本机以前见过的旧版本 | 不动，当作对方还没跟上 |

合并用的是 `git merge-file`，所以开发机上要有 git。

### 自动拉取

`pull.auto` 为 `true`（默认值）时，Claude Code 每次开始会话，hook 会先自动拉取一次，只做安全的更新：新建、覆盖本地没改过的文件、不重叠的自动合并。冲突只登记，不处理。整个过程最多 8 秒，超时就停下，并在会话开头的摘要里提示你手动执行 `kh pull`。

不想让任何东西自动写进仓库，把 `pull.auto` 改成 `false`。

## 处理冲突

会话开头的进度摘要会列出未解决的冲突。skill 要求 AI 先处理冲突再开始任务。手动处理的步骤是一样的：

```bash
kh conflicts                            # 列出所有冲突
kh conflicts show notes/plan.md
```

`show` 输出带合并标记的内容，分别标出本机、共同基准和对方机器的版本：

```
<<<<<<< 本机
本地的写法
||||||| 共同基准
原来的写法
=======
对方的写法
>>>>>>> desktop
```

二进制文件或没有共同基准时，改为输出两边的差异。

决定之后，三选一标记解决：

```bash
# 自己把本地文件改成合并后的内容，然后：
kh conflicts resolve notes/plan.md --edited

# 直接用对方的版本覆盖本地：
kh conflicts resolve notes/plan.md --take-remote

# 保留本地版本：
kh conflicts resolve notes/plan.md --take-local
```

全部解决后执行 `kh sync`，把最终内容推上去。

`kh conflicts` 和 `kh conflicts show` 读的是本机缓存，不联网也能用。

冲突没解决之前，这个文件照常推送本机的版本，服务端上对方的版本也保持不变，两边互不覆盖。

AI 处理冲突的规则写在 skill 里：两边的改动能兼容（改的是不同段落、都是补充内容），它会自己合并；两边对同一件事写法矛盾，或者拿不准以哪边为准，它会把差异给你看，问清楚再改。除非你同意，它不会为了省事直接整份采用一边的版本。

## 同时运行的保护

同一个项目的推送、拉取和解决冲突在本机共用一把锁。你手动执行时如果碰上后台同步正在进行，`kh` 会等最多 5 秒，还没轮到才报错“另一个同步或拉取正在进行”，稍后再试即可。hook 里的自动同步碰到锁被占用，直接跳过这一次。
