# 文档同步与冲突

kanban-hub 的服务端不读任何仓库的磁盘。你在网页上看到的文档，是各台机器上的 `kh` 推送上去的快照。这样服务端和开发机可以不在同一台机器上，一个项目也可以分散在好几台机器上。

同步只处理 `.kanban-hub/config.yaml` 里 `sync.include` 覆盖的文件，见《接入》的“同步范围”一节。

## 忽略规则

`include` 圈出的目录里常常夹着不该上传的东西：venv、克隆下来做参考的仓库、缓存目录。kh 按下面的顺序判断一个路径是否同步，前面的步骤先生效：

1. **始终排除**，不能覆盖：路径里任意一段是 `.git`（不分大小写）；仓库根的 `.kanban-hub/`；kh 的临时文件。
2. **`sync.include`**：不在 `include` 范围内的不同步。忽略规则只能在这个范围里往外剔，写 `!` 也不能把范围之外的路径加进来。
3. **忽略规则表**：内置规则在前，`.kanban-hub/ignore` 的内容在后，合成一份 `.gitignore` 语义的规则表。后面的规则覆盖前面的，`!` 开头的规则把已排除的路径加回来，父目录被排除时里面的路径一律排除。被排除的不同步；被 `!` 明确加回的同步，并且不再看第 4 步；没有规则命中的进入第 4 步。
4. **`sync.exclude`**（`config.yaml`）：命中的不同步。

内置规则排除这些目录和文件：

```
node_modules/  .next/  .venv/  venv/  __pycache__/  site-packages/
.pytest_cache/  .mypy_cache/  .ruff_cache/  .tox/  .gradle/  .idea/  .DS_Store
```

`build/`、`dist/` 这类目录没有内置排除，里面的文档照常同步。

### 按目录里的文件识别

推送扫描时，kh 还会看目录里有什么。下面两种目录整个跳过，视同被内置规则排除：

| 目录里有 | 识别为 |
|---|---|
| `pyvenv.cfg` | Python 虚拟环境 |
| `.git`（目录或文件），且该目录不是仓库根 | 嵌套的 git 仓库或工作树 |

这个识别只在推送扫描时做。`kh pull` 和 `kh conflicts resolve --take-remote` 只按路径判断，不看目录里有什么。

识别从 `include` 里不含通配符的目录前缀开始往下找，不看前缀本身的上级。例如 `include` 写 `vendor/lib/docs/**`，而 `vendor/lib` 是嵌套仓库，里面的 `docs/` 照常同步：显式指到里面，视为你的本意。

### 忽略文件 `.kanban-hub/ignore`

写法与 `.gitignore` 相同：`#` 开头是注释，空行忽略，`/` 结尾表示目录，开头的 `/` 表示从仓库根开始匹配，`!` 开头表示加回。文件不存在等于没有。匹配不分大小写（`docs/Drafts/` 也会排除 `docs/drafts/`），因为 macOS 的默认文件系统不分大小写；出错的方向是多排除。

```
# 追加排除
docs/drafts/
*.log

# 把被内置规则排除的目录加回来
!docs/vendor/venv/

# 把被识别为虚拟环境或嵌套仓库的目录加回来
!docs/ref-repo/
```

- 加回一个目录后，里面的内容继续按规则逐条判断：其中的 `__pycache__/` 仍被内置规则排除，`.git` 仍是始终排除。
- 被标记识别跳过的目录，只有它**自己**被 `!<目录>/` 加回才放行。写它上级目录的 `!` 不会放行。
- 对 `sync.exclude` 则相反：`!` 加回的目录，里面被 `sync.exclude` 排除的文件也一起放行，上级目录的 `!` 同样有效。
- `!` 规则尽量写具体的目录。通配的 `!` 影响面很大：`!*/` 或 `!*.md` 这类写法会让每个目录都算“自己被加回”，标记识别跳过的目录全部放行；单独一行 `!*.md` 会让所有 `.md` 越过 `sync.exclude`。
- `kh register` 新建配置时会生成一个全是注释的 `.kanban-hub/ignore` 模板；文件已存在则不动。在这个功能之前注册的仓库不会自动生成，需要时自己新建这个文件。

### 在多台机器间共享

`.kanban-hub/ignore` 位于 `.kanban-hub/` 内，默认不进 git。要让其他机器用同一份规则，在仓库里执行：

```bash
git add -f .kanban-hub/ignore
```

每台机器按自己本地的忽略文件推送。`kh pull` 按本机的忽略文件判定，被排除的路径不会写到本地。

### 预览：`kh sync --dry-run`

新建目录或批量生成文件之后，先看一眼将上传多少、上传什么类型的内容：

```bash
kh sync --dry-run
```

它只在本机扫描，不联网，不要求登录，也不改本机的同步状态。输出分几节，除第一节外，没有内容的节不出现：

- 将同步的文件数和总体积，再按一、二级目录汇总，不逐个列出文件（这一节总会输出）。
- 被跳过的目录和原因（内置规则、标记识别、忽略文件）。只列同步范围内的目录：`include` 够不到的目录（例如 `include` 是 `docs/**` 时的 `node_modules/`）不进入，也不列出。
- 超过大小上限而跳过的文件。
- 指向仓库外或已失效、已跳过的软链接。
- 文件类型建议：扩展名不在文档、网页、图片等常见类型里的文件，按扩展名列出数量和一个示例路径。这只是建议，不会拦截；不需要的文件加进 `.kanban-hub/ignore` 即可。

平时执行 `kh sync` 时，如果有目录因内置规则或标记识别被跳过，摘要末尾会多一行“按内置规则跳过了 N 个目录，执行 kh sync --dry-run 查看”。只由忽略文件排除的目录不计入 N，`--quiet` 时不输出。

### 升级之后

以前上传过 venv、嵌套仓库里的文件的话：

- 升级后下一次 `kh sync`，这些文件会从该机器的快照里消失，本地文件不动。
- 服务端数据目录的 git 历史里仍保留这些内容，体积不会缩小。
- 其他机器上的 kh 没升级的话，仍会从那边上传这类文件。
- 升级也不一定够：其他机器上通过 `kh pull` 得到的嵌套仓库副本没有 `.git`（`.git` 始终排除，从不上传也不拉取），升级后识别不出来，仍会当普通文件上传。需要在那台机器上删掉这个副本，或者在 `.kanban-hub/ignore` 里写上这个目录（可以 `git add -f .kanban-hub/ignore` 共享给各机器），再用 `kh sync --dry-run` 确认。venv 不受影响，`pyvenv.cfg` 会随拉取落地。

## 推送

```bash
kh sync
```

`kh sync` 只上传服务端还没有的内容，没变的文件不会重复上传。上传过程中断时，服务端的旧快照保持不变，下次重新同步即可。

装了 Claude Code hook 的话，你基本不用手动推送：每轮回复结束时，hook 会在后台推送一次。为了不拖慢会话，如果上次推送后什么都没变，而且距上次推送不到 10 分钟，它就直接跳过。所以网页上的“最后同步时间”可能比实际晚几分钟，手动执行 `kh sync` 则每次都会推送。

推送时顺带上报仓库的 git 状态：分支、最新提交、未提交的改动数、领先落后的提交数，显示在项目卡片和项目设置页上。

每台机器的快照在服务端分开存放，互不覆盖。

一些规则：

- 超过 `maxFileSize` 的文件不上传，在项目设置页的“跳过的文件”里列出。
- 指向目录的软链接不同步。指向文件的软链接，目标在仓库内时同步目标的内容，目标在仓库外或者已失效时跳过。
- 两个路径只差大小写（比如 `Readme.md` 和 `README.md`），服务端会拒绝整份清单，`kh` 会指出是哪两个路径。

## 跨机器读取

在一台机器上想参考另一台机器上没进 git 的文档，不用拉到本地，直接读：

```bash
kh docs ls                  # 列出其他机器快照里的文件
kh docs ls "notes/**"       # 按 glob 过滤
kh docs cat notes/plan.md
kh docs cat --from desktop notes/plan.md
```

不指定 `--from` 时，每个路径取其他机器里最新的那一份。

## 拉取

```bash
kh pull --dry-run    # 先看会发生什么
kh pull
```

拉取会把其他机器上的文档写进本地仓库，这是 `kh` 唯一会改动仓库文件的操作。它有几条底线：

- 被 git 跟踪的文件一律跳过。这些文件应该用 `git pull` 同步，kanban-hub 只负责没进 git 的文档。
- 拉取从不删除本地文件。对方删了某个文件，本地的照样保留。
- 本地删掉的文件，如果对方的版本是本机见过的旧内容，不会被拉回来。
- 只处理本机 `sync.include` 范围内的文件。

对每个文件，`kh` 会比较三份内容：本地当前的、对方的，以及两边上一次一致时的“基准”。结果有这几种：

| 情况 | 结果 |
|---|---|
| 本地没有这个文件 | 新建 |
| 本地没改过，对方改了 | 用对方的覆盖 |
| 本地改过，对方没改 | 保留本地 |
| 对方是在本地当前版本的基础上改的 | 直接覆盖 |
| 两边都改了，是文本，改的地方不重叠 | 自动合并，写入本地 |
| 两边都改了，改的地方重叠，或者是二进制文件 | 登记为冲突，本地文件不动 |
| 对方的内容是本机以前见过的旧版本 | 不动，当作对方还没跟上 |

合并用的是 `git merge-file`，所以开发机上要有 git。

### 自动拉取

`pull.auto` 为 `true`（默认值）时，Claude Code 每次开始会话，hook 会先自动拉取一次，只做安全的更新：新建、覆盖本地没改过的文件、不重叠的自动合并。冲突只登记，不处理。整个过程最多 8 秒，超时就停下，并在会话开头的摘要里提示你手动执行 `kh pull`。

不想让任何东西自动写进仓库，把 `pull.auto` 改成 `false`。

## 处理冲突

会话开头的进度摘要会列出未解决的冲突。skill 要求 AI 先处理冲突再开始任务。手动处理的步骤是一样的：

```bash
kh conflicts                            # 列出所有冲突
kh conflicts show notes/plan.md
```

`show` 输出带合并标记的内容，分别标出本机、共同基准和对方机器的版本：

```
<<<<<<< 本机
本地的写法
||||||| 共同基准
原来的写法
=======
对方的写法
>>>>>>> desktop
```

二进制文件或没有共同基准时，改为输出两边的差异。

决定之后，三选一标记解决：

```bash
# 自己把本地文件改成合并后的内容，然后：
kh conflicts resolve notes/plan.md --edited

# 直接用对方的版本覆盖本地：
kh conflicts resolve notes/plan.md --take-remote

# 保留本地版本：
kh conflicts resolve notes/plan.md --take-local
```

全部解决后执行 `kh sync`，把最终内容推上去。

`kh conflicts` 和 `kh conflicts show` 读的是本机缓存，不联网也能用。

冲突没解决之前，这个文件照常推送本机的版本，服务端上对方的版本也保持不变，两边互不覆盖。

AI 处理冲突的规则写在 skill 里：两边的改动能兼容（改的是不同段落、都是补充内容），它会自己合并；两边对同一件事写法矛盾，或者拿不准以哪边为准，它会把差异给你看，问清楚再改。除非你同意，它不会为了省事直接整份采用一边的版本。

## 同时运行的保护

同一个项目的推送、拉取和解决冲突在本机共用一把锁。你手动执行时如果碰上后台同步正在进行，`kh` 会等最多 5 秒，还没轮到才报错“另一个同步或拉取正在进行”，稍后再试即可。hook 里的自动同步碰到锁被占用，直接跳过这一次。
